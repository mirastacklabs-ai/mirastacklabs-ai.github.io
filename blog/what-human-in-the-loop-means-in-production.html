Almost everyone has it. Almost nobody has built it correctly."* --- ## The Checkbox Problem Open any enterprise AI vendor's product page. Scroll to the governance or safety section. You will find, within three paragraphs, the phrase "human in the loop." It is used to mean at least six different things: 1. A human set up the agent before it ran 2. A human can view logs of what the agent did after it ran 3. A human can terminate the agent session if something goes wrong 4. A human approves the agent's plan before it executes 5. A human approves specific high-risk actions during execution 6. A human can intervene at any point during execution and redirect These are not equivalent. They represent fundamentally different architectures with fundamentally different risk profiles. Most enterprise AI platforms, when pressed, implement versions 1, 2, and 3. Some implement version 4. A small number implement version 5. Version 6 is vanishingly rare. The question is not whether you have human in the loop. The question is: **at which points in agent execution does a human actually exercise control — and is that control enforced by the system or assumed by convention?** --- ## The Anatomy of an Agent Execution To understand where human control can and should occur, we need a precise picture of what an agent execution actually looks like. ```mermaid flowchart TD A([User Intent\nReceived]) --> B[Intent Classification\n& Scope Determination] B --> C{Intent Type?} C -->|Routine / Known| D[Load Runbook\nLane 1] C -->|Novel / Complex| E[Enter ReAct Loop\nLane 2] D --> F[Step 1: Validate inputs] F --> G[Step 2: Execute tool calls\nin dependency order] G --> H{All steps\ncomplete?} H -->|Yes| I[Synthesize result] H -->|No - blocked| J[Report partial result] E --> K[LLM reasons about\nnext tool call] K --> L[Engine validates\ntool call] L --> M{Validation\nresult?} M -->|Valid READ| N[Execute immediately] M -->|Valid MODIFY/DESTROY| O{Pre-approved\npattern?} M -->|Invalid schema| P[Return error to LLM\nSelf-correction] M -->|Exceeds permissions| Q[Hard stop\nReport to user] O -->|Yes| N O -->|No| R[🔴 HUMAN GATE\nApproval Required] N --> S{Budget\nremaining?} S -->|Yes| K S -->|No| T[Checkpoint state\nReport progress] R --> U{Human decision?} U -->|Approved| N U -->|Rejected| V[Skip action\nContinue with alternatives] U -->|Timeout| W[Escalate or abandon\nPer policy] I --> X([Result delivered\nAudit trail complete]) J --> X T --> X V --> X W --> X style R fill:#FF671F,color:#fff style Q fill:#E8456A,color:#fff style P fill:#4A5563,color:#fff ``` There are five potential human control points in a well-designed execution: 1. **Intent review** — before the agent begins, a human confirms the scope is appropriate 2. **Plan approval** — for Lane 1 runbooks, a human reviews the planned steps before execution begins 3. **Action gates** — during execution, specific action tiers require explicit human approval 4. **Redirect** — during execution, a human can modify the agent's direction based on what they observe 5. **Revocation** — at any point, a human can terminate the session The question of which control points are active, for which action types, under which conditions — this is the governance policy. And the governance policy should be enforced by the system, not honored by convention. --- ## The Three Architectures In practice, enterprise agentic AI deployments fall into three broad architectures for human-in-the-loop implementation: ### Architecture 1: Post-Hoc Review (Most Common) The agent runs autonomously. Humans review logs afterward. If something went wrong, there is a record of what happened. ```mermaid sequenceDiagram participant Human participant Agent participant System Human->>Agent: Start session Agent->>System: Tool call 1 Agent->>System: Tool call 2 (MODIFY — unchecked) Agent->>System: Tool call 3 (DESTROY — unchecked) Agent->>System: Tool call 4 Agent->>Human: Task complete Human->>Agent: Show me what you did Agent->>Human: Here are the logs Note over Human: Reviews logs AFTER all actions taken Note over Human: No ability to intervene during execution Note over Human: "Human in the loop" ✓ (checkbox) ``` **Risk profile:** High. The human is not in the loop during execution — they are in the loop in the postmortem. This is observability, not governance. ### Architecture 2: Plan-and-Execute (Better) The agent proposes a plan. A human approves the plan. The agent executes. ```mermaid sequenceDiagram participant Human participant Agent participant System Human->>Agent: Start session Agent->>Human: Proposed plan: [Step 1, 2, 3, 4] Human->>Agent: Plan approved Agent->>System: Execute Step 1 Agent->>System: Execute Step 2 (MODIFY — plan pre-approved) Agent->>System: Execute Step 3 (DESTROY — plan pre-approved) Agent->>System: Execute Step 4 Agent->>Human: Task complete Note over Human: Approved the plan, not each action Note over Human: Step 3 was planned as "clean up resources" Note over Human: Did not realize it would delete the DR snapshot ``` **Risk profile:** Medium. Better than post-hoc review, but plan approval does not equal action-level approval. Edge cases during execution are still ungoverned. ### Architecture 3: Action-Gated Execution (What Production Requires) Specific action tiers trigger mandatory human approval at execution time, not at planning time. ```mermaid sequenceDiagram participant Human participant Agent participant Engine as Governance Engine participant System Human->>Agent: Start session Agent->>Engine: Tool call: query_metrics (READ) Engine->>System: Auto-approved — execute System-->>Engine: Data returned Engine-->>Agent: Result Agent->>Engine: Tool call: scale_deployment (MODIFY) Engine->>Human: ⏸️ Approval required Engine->>Human: Action: scale payment-svc 3→8 replicas Engine->>Human: Reason: latency spike correlation Engine->>Human: Risk: moderate — reversible Human->>Engine: ✅ Approved Engine->>System: Execute with authorization record Agent->>Engine: Tool call: delete_snapshot (DESTROY) Engine->>Human: 🔴 Approval required — DESTROY tier Engine->>Human: Action: delete snapshot snap-0a3f (DR backup) Engine->>Human: Risk: HIGH — irreversible Human->>Engine: ❌ Rejected — this is our DR snapshot Engine->>Agent: Action rejected by human. Reason: DR asset protection. Agent->>Engine: Acknowledged. Will seek alternative approach. Note over Human,Engine: Human was IN the loop at the right moment Note over Human,Engine: Not reviewing a plan. Not reviewing logs. Note over Human,Engine: Exercising real-time control at decision points that matter. ``` --- ## The Practical Problem With Architecture 3 I want to be honest about the challenge here. Architecture 3 is clearly correct from a governance perspective. It is also the hardest to implement well because it creates latency in agent execution — every action gate requires a human to be available and responsive. If your agent makes 40 tool calls in a session, and 8 of them are MODIFY or DESTROY tier, you need 8 human approval decisions. If the human takes 3 minutes per decision, that's 24 minutes of human time plus agent idle time. For a 3 AM incident response, that might mean the on-call engineer is in the loop for an agent session that would otherwise run in 12 minutes. This is a real operational tradeoff. Here is how well-designed governance handles it: ```mermaid flowchart LR subgraph "Pre-approved Patterns" A[Common MODIFY actions\nthat are low-risk and\nwell-understood] B[Defined in governance\npolicy per environment] C[Auto-execute within\npre-approved envelope] end subgraph "Real-time Gates" D[Novel MODIFY actions\nnot matching any\npre-approved pattern] E[All DESTROY actions\nregardless of pattern] F[All ADMIN actions] end subgraph "Approval Optimization" G[Mobile-first approval UI\nContext + risk shown clearly] H[Timeout policies\nper action tier] I[Escalation chain\nif primary unavailable] J[Async approval\nagent pauses and resumes] end A --> C B --> C D --> G E --> G F --> G G --> H H --> I I --> J ``` The key insight: **not every MODIFY action requires a real-time human gate.** Well-understood, low-risk, reversible modifications within a pre-approved policy envelope can execute automatically with full audit logging. Real-time gates should be reserved for actions that are novel, high-risk, irreversible, or outside the pre-approved envelope. This is the difference between "human in every loop" (operationally impractical) and "human at the right loops" (operationally sustainable and genuinely governed). --- ## What "The Right Loops" Actually Means Determining which loops require human gates is a policy decision, not a technical one. But it requires technical infrastructure to enforce. Here is a framework we use: | Action Tier | Risk Profile | Human Gate? | Gate Type | |---|---|---|---| | READ | Low. No state change. Reversible by definition. | No | Audit log only | | MODIFY — pre-approved pattern | Low-medium. Reversible. Within known envelope. | No | Audit log only | | MODIFY — novel pattern | Medium. Reversible but unanticipated. | Yes | Async — agent pauses | | MODIFY — outside business hours | Medium-high. No immediate human context. | Yes | Async — wake on-call | | DESTROY | High. Irreversible by definition. | Yes | Synchronous — must confirm | | ADMIN | Critical. Affects permissions and policy. | Yes | Synchronous + dual approval | The policy is configurable per environment (dev environments may have lower gates than production), per user role (L3 engineers may have larger pre-approved envelopes than L1 operators), and per time window (business hours vs. off-hours). --- ## The Enforcement Question One final point, and it is the most important one in this article. A human-in-the-loop policy that lives in documentation but is not enforced by the system is not a governance control. It is a guideline. Guidelines are followed when it is convenient to follow them and bypassed when it is not. Real human-in-the-loop means the agent **cannot** execute a DESTROY action without a human approval record in the system. Not "should not." **Cannot.** The enforcement is at the engine layer, not the application layer. If the approval system is down, the action waits or fails — it does not silently proceed. If the approval is not received within the timeout window, the escalation chain activates — it does not silently proceed. If the human approval record does not exist, the execution record is invalid — it does not silently proceed. **Enforced at the engine. Not assumed at the application. That is the difference between a governance control and a checkbox.** ---
