MCP inside the perimeter

MCP servers run as governed runtimes inside your network. Credentials never leave the platform's secret store. Every tool classified READ / WRITE / MODIFY / ADMIN by an operator. Every dispatch ledgered with the human actor who authorised it. Runs in networks with no internet route at all.

The containment invariant is enforced, not documented: the child MCP process must bind loopback. Never 0.0.0.0. There is no configuration that turns that off.

runtime.lifecycle

Runtime registration lifecycle

The MCP Harness manages the full lifecycle of every server: registration, classification, secret injection, dispatch, and teardown. The operator defines what each server is allowed to do. The runtime enforces it.

↓
2. Credentials injected from secret store

↓

↓
5. Agent dispatch through governance gate
↓
6. Result ledgered and returned
classification.model

The classification model

Every tool exposed by an MCP server is classified by the operator, not inferred from the payload. The classification determines whether the dispatch proceeds immediately, requires approval, or is refused outright.

READ

Read

Queries, lookups, and metadata retrieval. No state modification. Proceeds without approval unless the target is classified as sensitive by policy.

WRITE

Write

Create and append operations. Existing state is not altered. Actor and content hash recorded on the ledger. May require approval depending on target sensitivity.

MODIFY

Modify

Updates to existing state. Always requires explicit operator approval unless a standing rule exists for this actor-target pair.

ADMIN

Admin

Structural changes: schema, accounts, access control. Always requires a single-use, signature-verified approval bound to the exact action hash.

loopback.containment

Loopback containment

The child MCP process must bind loopback. Never 0.0.0.0. There is no configuration that turns that off. This is enforced by the runtime before the first tool call is accepted, and verified on every restart.

Containment is not a network policy you write. It is a property of the runtime. If the child process cannot bind loopback, it does not start. If it loses loopback binding after start, the runtime tears it down and refuses further dispatches until the operator re-registers it.

air.gapped.deployment

Air-gapped deployment

The MCP Harness runs in networks with no internet route at all. Model weights, tool runtimes, and the governance engine are all deployed inside the perimeter. No outbound call is required for the platform to function.

Air-gapped deployment is not a deployment option — it is the design baseline. Every component is resolvable from internal registries. Every secret is injected at runtime from the platform's secret store. No hardcoded endpoints, no embedded API keys, no phone-home telemetry.
