Governance — EGAProtocol in the platform

Every plugin execution and every MCP tool call passes one approval gate before dispatch. The governance plane is not a middleware layer — it is the dispatch path itself. Bypassing it is a compile error, not a policy violation.

the.single.gate

The single dispatch gate

When an agent issues a tool call, the runtime does not execute the tool — it submits the dispatch to EGAProtocol first. The gate classifies the action, evaluates standing rules, and, if required, requests approval before the tool ever runs.

This is not a callback or a decorator inside the agent framework. It is a stateless security proxy that sits at the wire boundary. Every message envelope passes through it, regardless of which framework produced the message.

1. Agent emits tool_call
↓
2. EGAProtocol classifies the action
↓
3. Policy engine evaluates standing rules
↓
4. Approval gate if required
↓
5. Dispatch recorded on the ledger
↓
6. Tool executes inside the runtime
permission.classes

Four permission classes

Every action an agent takes is classified before dispatch. The classification is set by the operator, not inferred from the payload. Four classes cover every possible side effect an enterprise agent can produce.

READ

Observation only

Queries, searches, metadata lookups, and read-only API calls. No state is modified. Audit log records the query, the target, and the actor.

WRITE

Create and append

New records, messages, tickets, and artifacts. Append-only semantics where possible. Existing state is not altered. Actor and content hash are recorded.

MODIFY

Update existing state

Configuration changes, record updates, permission changes. Requires explicit operator approval unless the policy engine has a standing rule for this actor and this target.

ADMIN

Structural changes

Schema changes, account creation or deletion, access control modifications. Always requires a single-use, signature-verified approval bound to the exact action hash. The requester cannot approve their own request.

approval.semantics

Approval semantics

Approvals in EGAProtocol are not frontend buttons. They are cryptographic primitives that live in the governance engine. Every approval is single-use, signature-verified, and bound to the exact action hash it authorises.

› Single-use tokens. Once an approval is consumed, it cannot be replayed against a different action hash or a different session.
› Actor separation. The requester and the approver must be distinct principals. Self-approval is refused at the engine level, not filtered in a UI.
› Time-bound validity. Approvals expire after a configurable window. Expired approvals require a new request and a new approval flow.
› Revocation propagation. Revoking a principal invalidates all outstanding approvals in flight. The effect is immediate across every tenant and every runtime.
the.audit.ledger

The audit ledger

Every dispatch writes a pass object to the audit ledger before execution begins. If execution fails, the ledger still records the attempt, the actor, the target, and the reason. Every token, cost, and latency metric is attached to that same entry.

The ledger is append-only and tamper-evident. Records follow OpenTelemetry semantic conventions, so they can be ingested by the observability stack without transformation. An auditor receives a single, replayable evidence pack — not a log export.

what.an.auditor.receives

What an auditor actually receives

The evidence pack is generated on demand and contains exactly what the auditor needs, nothing more and nothing less. It maps to the control frameworks the auditor already uses.

› Attribution. Every action linked to a named human principal with timestamp and source IP.
› Approval chain. Full approval or decline trail with signer identity, signature, and binding action hash.
› Routing decision. Which model or tool was selected, why, and what data classification was applied.
› Token accounting. Prompt and completion tokens, cost, and latency for every turn in the interaction.
